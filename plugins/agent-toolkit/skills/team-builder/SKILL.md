# Team Builder

## Execution boundary

Check authority before capability. Default STANDARD + SOLO; preserve explicit
accepted task profile/topology and current exclusions. Planning or selecting
roles does not authorize a worker. HANDOFF, PARALLEL and REVIEW require explicit
user authorization before changing actors. Never launch another CLI, worker or
orchestrator to bypass a restriction. Check actual exposed tools/schemas only
after authority; availability alone grants no action.

If requested capability is missing, disclose it and use SOLO/manual execution only
when consistent with user intent. Do not relabel local role passes as independent
review or fabricate tool/background success. Reuse existing specific authority
within scope; no repeated permission menu. Keep the configured model unless a
change is authorized. Mandatory project gates and worktree-first always apply.
Consult the existing development-lifecycle-rules contract when installed; this
plugin's safe local path requires no other plugin or copied skill catalog.

## Discover and propose roles

Read the current request and accepted role choices; do not force another picker
when intent is already clear. Inspect only exposed metadata, applicable shared
AGENTS policy, requested role directories and installed shared role descriptions.
Native Claude definitions can describe host roles; Markdown agents do not register
Codex native agents. CLI inventory is subject to session authority and any
no-other-harness restriction; do not launch it as a discovery shortcut when denied.
Preserve source identities when names collide; do not invent agents or install
host configuration.

Propose a small relevant set (normally up to five roles), explain overlap and
ownership. Choosing architecture/testing/security roles is not permission to spawn
those actors. Record topology authorization separately from role applicability.
A request for a local role pass keeps SOLO; an explicit separate team/reviewer
request can authorize that topology only within its stated scope.

## Execute only the selected scope

Use local sequential role passes in SOLO. When an actor topology is explicitly
authorized, verify actual tooling and brief objective/context, scope/exclusions,
checks, owner/integrator and completion evidence before dispatch. Concurrent writers
need distinct branch/worktree; read-only sharing is allowed only under authorized
review scope. No repeated permission question for an already approved actor/scope.

Collect findings and disclose failures, partial results and lack of independence.
A failed role blocks dependent integration; do not claim a whole team succeeded
from partial reports. Missing requested actor capability is a limitation, not a
silent topology change. Stay within the selected task/stage; report next action
without implied commit/push/PR, merge or runtime mutation.
